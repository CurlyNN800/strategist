# Маршрутизация моделей (черновик)

Принцип: дорогая модель — там, где нужно рассуждать; дешёвая — там, где работа механическая
и результат проверяется скриптом. Конкретные модели команда выбирает в день 1 и вписывает сюда.

| Роль | Модель | Ключ в `.env` |
| --- | --- | --- |
| Сильная | _выбрать_ | `STRONG_MODEL_API_KEY` |
| Дешёвая | _выбрать, кандидат — GigaChat_ | `CHEAP_MODEL_API_KEY` |

## Какая задача какой моделью

| Задача | Модель | Почему | Как проверяется |
| --- | --- | --- | --- |
| Уточнение постановки (01) | сильная | важно понять, какие вопросы меняют решение | подтверждение пользователя |
| Извлечение утверждений из источника (02) | дешёвая | механическая работа, много текста | схема evidence + валидатор |
| Классификация записи: fact / hypothesis / … | дешёвая | выбор из 4 вариантов | валидатор: fact без источника не проходит |
| Сопоставление источников, гипотезы (03) | сильная | рассуждение | валидатор + auditor |
| Варианты и стратегии (04, 06) | сильная | главная ценность результата | red-team + auditor + рубрика |
| Red-team возражения | сильная | слабые возражения бесполезны | рубрика |
| Модельные респонденты | дешёвая | ответы и так помечаются синтетикой | тип `synthetic` |
| Сборка отчёта (07) | скрипт | без модели | — |

## Исправление ошибочного выбора

1. Дешёвая модель вернула результат → запускается `validate.py`.
2. Валидатор упал на её записях → те же записи переделывает сильная модель.
3. В `log.md`: «повтор на сильной модели: причина …»; в `cost.csv` видны обе попытки.

Если за этап дешёвая модель ошиблась больше двух раз — этот тип задач до конца
задачи отдаётся сильной модели (записать в `log.md`).

## Ограничения среды

Не каждая среда позволяет выбирать модель для субагента. Где нельзя — маршрутизация
делается вызовом API дешёвой модели из скрипта (роль Б) или отключается; фиксируем
в `docs/compatibility.md`.
