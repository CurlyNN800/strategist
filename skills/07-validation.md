# 07-validation — план проверки и итоговый отчёт

**Цель:** понять, как узнать, что стратегия сработала, и собрать итог для руководителя.

**Вход:** `decision.md`, `product-strategy.md`, `comms-strategy.md`, `evidence.jsonl`.

## Шаги

1. Для каждого ключевого ожидания из стратегий заполни в `validation-plan.md`:
   - **ожидаемое изменение** — метрика, направление, величина (как `forecast`);
   - **с чем сравниваем** — контрольная группа, период до, когорта;
   - **срок наблюдения** — когда смотрим и почему именно тогда;
   - **нежелательные последствия** — что может ухудшиться и какой порог остановит эксперимент.
2. Запиши решение и обязательства в реестр решений (журнал `decisions.md` соберётся сам):
   ```
   python scripts/decision.py add <task> --title "<решение>" --option <№> --grounds E…,E… --owner "<роль, не имя>" --metric "<метрика из плана>" --review-if "<условие>" --review-by <дата>
   python scripts/decision.py commit <task> D1 --what "<что сделать>" --owner "<роль>" --due <дата> --ref P…
   ```
   Обязательства — ключевые шаги из `product-strategy.md` и `validation-plan.md` (запуск, замер,
   точка решения). Ответственных и сроки предложи, но подтверди у пользователя.
   `python scripts/decision.py check <task>` — покажи пользователю, что из этого решать сейчас.
3. Напиши `summary.md` — 5–7 строк для руководителя: что рекомендуем, почему (с метками `[E…]`),
   главный риск, чего не знаем, что решить сейчас.
4. **Есть `requirements.md`** — напиши `deliverable.md` по шаблону `knowledge/templates/deliverable.md`:
   - разделы и их порядок — ровно как требует бриф; начало документа — то, что бриф просит в начале;
   - содержание бери из рабочих файлов этапов, метки `[E…]` и `[P…]` сохраняй;
   - расчёты ставь рядом с решениями, которые они обосновывают (таблица + вывод + метка расчёта);
   - у каждого места, которое закрывает требование, ставь `[R…]`; в конце — таблица
     «Соответствие требованиям брифа». Требование не закрыто — так и пиши в таблице, почему и что нужно;
   - начало документа — кто клиент, проблема, предложение, ожидаемый результат, главный риск и просьба; каждое число
     из начала сверь с числом в разделах;
   - пороги проверки — только различимые к своей дате (`knowledge/methods/experiments.md`, «предел различимости»);
     проверь это в каждом сценарии (основном и неблагоприятном): если в одном вывод к дате невозможен — назови дату,
     когда он будет, и что решают без него; расширение не начинай раньше окончательной проверки, которая его обосновывает;
     ресурсы — доля ставки × месяцы до последней точки решения (`knowledge/methods/planning.md`);
   - субагент `agents/auditor.md` проверяет документ по `requirements.md` и `knowledge/rubric.md`. **Обязательно**:
     исправь блокирующие замечания, отзови записи с ошибками (`evidence.py revoke`), найди, где они использованы
     (`revise.py`), и запусти аудитора ещё раз, пока блокирующих не останется.
5. `python scripts/build_report.py <task> --clean` → `report.md` (с метками и приложениями — для проверки)
   и `report-clean.md` (для руководителя: без служебных меток, ссылки на утверждения — сносками).
6. `python scripts/validate.py <task>` — перед показом отчёта.

## Выход

`validation-plan.md`, `decisions.md`, `summary.md`, `report.md`; при наличии требований — `deliverable.md`.

## Проверка перед завершением

- [ ] У каждого ожидания есть сравнение, срок и нежелательные последствия.
- [ ] `report.md` читается без остальных файлов.
- [ ] Если есть `requirements.md` — каждое `R…` закрыто или в таблице соответствия объяснено, почему нет.
- [ ] Валидатор без ошибок. `python scripts/state.py stage <task> 07-validation done`.
- [ ] Скажи пользователю: работа завершена; при новых данных — «новые данные …»;
      что решать дальше — «что решать?» (`decision.py check`).
